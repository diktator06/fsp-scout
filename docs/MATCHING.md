# Механика подбора: «Скаутинг»

Работодатель в «Скауте» не разбирает поток откликов. Он описывает потребность и получает
ранжированную подборку кандидатов из банка, где все уже разложены по категориям тестом.
Затем приглашает конкретного человека, и вилка зарплаты в приглашении обязательна.
Кандидат видит компанию и зарплату сразу. Свои контакты он раскрывает сам, если принимает
приглашение.

```
Потребность (текст) → разбор → категории с рыночным срезом → подборка v1, v2…
  → обезличенная карточка → приглашение с вилкой → принятие → раскрытие контактов
```

## 1. Потребность из свободного текста

Работодатель пишет так, как написал бы коллеге: «Python-разработчик (Middle), FastAPI,
PostgreSQL, будет плюсом Kafka, удалённо, 230–320 тыс.». Разбор работает на правилах и
справочнике навыков, без внешних нейросетей. Поэтому результат воспроизводим и работает
офлайн.

| Поле | Как находится |
|---|---|
| Навыки | 152 навыка с синонимами («питон», «постгрес», «k8s»). Более длинное совпадение маскирует короткое: «React Native» не даёт ещё и «React». Двухбуквенные имена (Go, JS) ищутся только с заглавной |
| must / nice | Маркеры «будет плюсом», «желательно», «nice to have» в строке или заголовке списка переводят навыки в желательные |
| Специализация | Ключевые слова («бэкенд», «аналитик данных», «тестировщик») плюс веса найденных навыков по специализациям |
| Грейд | Явно (Middle, «сеньор», «стажёр») или из стажа: «опыт от 3 лет» → Middle |
| Вилка | «от 200 000 до 280 000 ₽», «180k–250k», «до 300 тыс.»; база — «на руки» или «до вычета НДФЛ» |
| Формат и город | «удалённо», «гибрид», «офис»; 20 крупных городов во всех падежах. «Гибрид, офис в Казани» — это гибрид, а не два формата |

У каждого найденного значения есть фрагмент исходного текста. Работодатель видит, откуда
взялось поле, и правит его перед сохранением.

## 2. Жёсткие фильтры

В пул попадают только кандидаты, которые:

- дали **отдельное согласие на публикацию** в банке (152-ФЗ). Отзыв согласия сразу убирает
  человека из поиска;
- не выбрали статус «не ищу»;
- относятся к специализации потребности и допустимым грейдам. Грейд берётся из категории,
  присвоенной тестом, а если её нет — заявленный в опросе. Флажок «соседние грейды»
  расширяет грейд на ±1.

## 3. Индекс подтверждённого профиля (ранг внутри категории)

```
VPS = 100 · (0,55·T + 0,20·M + 0,15·F + 0,10·P)
```

- **T — тест.** Перцентиль θ среди подтверждённых коллег по категории, умноженный на
  поправку точности (1 − SE²/2) и на затухание давности (период полураспада — год).
  Экспресс-тест учитывается с коэффициентом 0,85. Пока в категории меньше восьми
  подтверждённых кандидатов, перцентиль считается по положению θ в полосе категории на
  шкале.
- **F — достижения ФСП:** `min(1; 0,6·R + 0,4·N)`, где R — результативность, N — активность.
  Уровень и дисциплина соревнований на балл не влияют. Без привязки, без истории или со
  скрытыми достижениями F = 0: это не штраф, а отсутствие бонуса, и карточка говорит об этом
  нейтрально. Подробности и примеры — в [FSP_INTEGRATION.md](FSP_INTEGRATION.md).
- **M — микрозадачи.** Пока равен 0 (шаг 6), тоже без штрафа.
- **P — подтверждённость профиля:** email, заполненность, навыки, подтверждённые тестом.

## 4. Балл соответствия потребности

```
Match = 0,35·Skills + 0,35·VPS/100 + 0,15·Semantic + 0,15·Conditions
```

| Фактор | Расчёт |
|---|---|
| Skills | Σ wₛ·cred / Σ wₛ; w = 2 для обязательного навыка, 1 для желательного. cred = 1,0, если навык подтверждён тестом; 0,7, если заявлен и типичен для специализации; 0,5 — в остальных случаях. Отсутствующий навык частично закрывается родственным: 0,5 × похожесть (75 пар: Django ≈ FastAPI 0,6, PostgreSQL ≈ MySQL 0,7…) |
| Semantic | Косинус TF-IDF между описанием задач команды и рассказом кандидата («о себе» и опыт). Используются лёгкий русский стемминг и синонимы навыков. IDF считается по пулу этой же потребности, поэтому редкие слова («эквайринг», «геоданные») весят больше общих |
| Conditions | Произведение трёх проверок. Зарплата: ожидания и вилка сравниваются в одной базе, «на руки» ÷ 0,87; 1, если ожидания не выше «до», дальше линейно до 0 при 1,3 × «до». Формат: совпадение или 0,4. Город: важен только для офиса и гибрида, готовность к переезду даёт 0,9 |

Поверх формулы действуют понижающие множители. **Неподтверждённый грейд — × 0,75**: по
просьбе менторов такие кандидаты видны, но ниже в выдаче. **Соседний грейд — × 0,85.**
Веса стартуют экспертными. Подбор весов на размеченных парах «потребность — кандидат»
запланирован на шаг 6. Версия алгоритма (`match-1.0`) записывается в каждую подборку.

### Приватность в ранжировании

Если кандидат скрыл ожидания или город, подбор их **не использует**. Условие считается
неизвестным с нейтральным значением, а в объяснении написано «скрыты». Иначе по порядку
выдачи можно было бы догадаться о том, что человек решил не показывать. По той же причине
медиана ожиданий в рыночном срезе строится только по открытым ожиданиям и показывается
при n ≥ 3.

## 5. «Почему в подборке»

У каждого кандидата есть кольцо балла, полоса вкладов четырёх факторов и список причин из
тех же чисел, из которых сложился балл:

- ✓ Закрывает 3 из 3 обязательных навыков: Python, FastAPI, PostgreSQL
- ✓ Подтверждено тестом: Python, Docker
- ≈ A/B-тестирование — нет, но есть родственный «Статистика»
- ✗ Нет в профиле: pandas
- ✓ Тест: 78-й перцентиль в категории «Аналитика данных · Junior»
- ✗ Грейд заявлен, но не подтверждён тестом
- ✓ Ожидания укладываются в вашу вилку
- ✓ Опыт перекликается с задачами: эквайринг, биллинг
- ✓ ФСП: призёр (2 место из 140): Кубок «Северное сияние», 2025 — или нейтральное
  «Профиль ФСП не привязан — оценка по тесту и профилю»

## 6. Рынок, версии и отметки

- **Рекомендованные категории.** Целевая категория, соседние грейды и смежная
  специализация (backend ↔ devops, frontend ↔ mobile, аналитика ↔ ML). По каждой
  показано: сколько кандидатов и сколько из них подтверждено, сколько закрывают весь
  обязательный стек, сколько сильных (Match ≥ 0,6), медиана ожиданий и «в вилке / выше
  вилки».
- **Версии.** Каждое уточнение (только подтверждённые, навык подтверждён тестом, формат,
  город, «в вилке», «есть ФСП», минимальный балл, соседние грейды) создаёт новую версию
  подборки.
  Старые версии доступны в переключателе. Балл и объяснение хранятся снимком версии, а
  карточка всегда актуальная.
- **Отметки.** «Закреплён» переносится во все следующие версии, даже если кандидат не
  проходит новые фильтры: это требование ТЗ «уточнять без потери подборки». «Скрыт»
  исключает кандидата из следующих версий.

## 7. Обезличенная карточка и раскрытие контактов

- Схема `CandidateAnonymousCard` **физически не содержит** ФИО, email, телефона и Telegram:
  контакты нельзя отдать случайной сериализацией.
- Контакты приходят отдельным объектом и только через `ContactAccessPolicy`. Её
  единственный источник права — запись в `contact_disclosures`. Каждое раскрытие пишется
  в журнал аудита.
- Раскрываются только каналы, которые кандидат разрешил в настройках приватности. Названия
  прошлых работодателей, город и ожидания показываются, только если кандидат это включил.
- Контакты, оставленные в тексте «о себе» (email, телефон, ник, ссылка), маскируются меткой
  «[скрыто]».

## 8. Приглашение

| Правило | Реализация |
|---|---|
| Вилка «от–до» обязательна (R2) | CHECK в базе, проверка в схеме и в форме; «до» не больше чем вдвое выше «от»; явная база: до вычета НДФЛ или на руки |
| Описание и способ связи (R3) | Обязательные поля |
| Статусы видны обеим сторонам (R5) | `sent → viewed → accepted / declined`, отзыв работодателем, истечение через 14 дней; журнал переходов — таймлайн у обеих сторон |
| Контакты только после принятия (R4) | Принятие и раскрытие — одна транзакция |
| Изоляция (R11) | Чужое приглашение, потребность или кандидат — 404 |
| Против массовых рассылок | Одно активное приглашение на пару «компания — кандидат» (частичный уникальный индекс), дневная квота по уровню доверия компании (20 / 50 / 100) |
| Обратная связь | Причина отказа видна работодателю; уведомления в кабинете и письма |

Перед отправкой интерфейс предупреждает, если открытые ожидания кандидата выше верхней
границы вилки: отказ почти гарантирован.

## 9. Демо-данные

При первом старте стенд создаёт около 120 вымышленных кандидатов по семи
специализациям. Каждый проходит адаптивный тест **настоящим сервисом оценки**: ответы
разыгрываются по модели IRT от «истинной» способности, время ответов правдоподобно, тесты
разнесены по году. Поэтому категории, подтверждённые навыки и индексы получаются по тем же
правилам, что у живых людей. Демо-компания «Кедр Технологии» (вымышленная) получает две
потребности.

Генератор нашёл настоящую ошибку движка тестирования. Параллельные сессии брали блокировки
счётчиков семейств заданий в разном порядке и попадали во взаимоблокировку. Теперь
счётчики применяются в конце транзакции по возрастанию id.

## 10. Ограничения и следующие шаги

- Веса формул экспертные. Нужен подбор на размеченных парах и сравнение с keyword-бейзлайном
  (P@10, nDCG@10) — это шаг 6 плана.
- Semantic — TF-IDF. Офлайновые эмбеддинги (fastembed) улучшат синонимию описаний.
- Фактор M (микрозадачи) появится на шаге 6. Пока индекс подтверждённого профиля не
  превышает 80.
- Квоты и уровень доверия задаются платформой. Проверка ИНН, домена и жалобы — в концепции
  защиты от фиктивных вакансий.
