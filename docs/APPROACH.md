# «Скаут»: механика подбора и адаптивное тестирование

Краткое описание и обоснование двух главных механик для промежуточной сдачи (§5.1 ТЗ). Подробные
методики — в [MATCHING.md](MATCHING.md), [ASSESSMENT.md](ASSESSMENT.md) и
[FSP_INTEGRATION.md](FSP_INTEGRATION.md), сценарий для проверки — в [README](../README.md).

**Идея в одном абзаце.** Категорию кандидату («Backend · Middle») присваивает не резюме, а опрос
и адаптивный тест. Поэтому работодатель ищет не по ключевым словам в самоописании, а по
категории, подтверждённым навыкам и индексу профиля. Инициатива контакта у работодателя: он
описывает потребность, получает ранжированную подборку с объяснением каждого места и приглашает
конкретного человека с обязательной вилкой. Контакты кандидата открываются только после его
согласия.

## 1. Механика подбора — «скаутинг» (критерий 35 %)

### 1.1 Сценарий контакта для обеих сторон

```
Работодатель                                   Кандидат
описывает потребность текстом                  опрос → тест → категория
  → разбор: стек (must/nice), грейд,           публикация в банке (согласие)
    формат, город, вилка — с источником        привязка ФСП ID (по желанию)
  → рекомендованные категории с рынком
  → подборка v1 с «Почему в подборке»
  → уточнения = новые версии, закреплённые
    кандидаты сохраняются
  → приглашение с вилкой «от–до»  ───────────►  видит компанию, вилку и описание сразу
                                                 принимает или отклоняет с причиной
  ◄─────────── контакты кандидата ─────────────  (раскрытие = принятие, одна транзакция)
```

Для кандидата это отсутствие откликов в пустоту: зарплата видна до начала общения, а контакты
под его контролем. Для работодателя — короткий шорт-лист людей с подтверждённым уровнем вместо
потока резюме.

### 1.2 Почему именно так

| Решение | Обоснование | От чего отказались |
|---|---|---|
| Потребность пишется свободным текстом | Работодателю не нужно учить форму; разбор показывает, из какого фрагмента взято каждое поле, всё правится до сохранения | Многошаговая анкета вакансии: долго, и стек всё равно пишут текстом |
| Разбор на правилах и справочнике (152 навыка с синонимами) | Воспроизводимо, объяснимо, работает офлайн на стенде без GPU | Внешняя LLM: недоступна офлайн, непредсказуема, сложно объяснить ошибку |
| Сначала категории, потом люди | Работодатель видит размер рынка: сколько кандидатов, сколько подтверждённых, медиана ожиданий относительно вилки | Сразу список людей: непонятно, не слишком ли узкий запрос |
| Ранг внутри категории — индекс подтверждённого профиля | Растёт только от проверяемых сигналов: тест, ФСП, подтверждённость профиля | Ранг по заполненности резюме: поощряет самоописание |
| Неподтверждённый грейд виден, но ниже (×0,75) | Так просили менторы: не скрывать, а опускать | Скрывать до теста: работодатель теряет часть рынка |
| Вилка обязательна и не шире чем вдвое, база НДФЛ явная | Требование ТЗ (R2) и защита от «вилок» вида 50–500 тыс. | Необязательная зарплата: главная претензия кандидатов к рынку |
| Скрытые кандидатом данные не участвуют в ранжировании | Иначе по месту в выдаче можно восстановить скрытые ожидания или город | Учитывать всё: утечка через порядок выдачи |

### 1.3 Ранжирование

```
VPS   = 100 · (0,55·T + 0,20·M + 0,15·F + 0,10·P)              ранг внутри категории
Match = 0,30·Skills + 0,20·VPS/100 + 0,15·Semantic + 0,35·Conditions
```

- **T** — перцентиль оценки θ среди подтверждённых коллег по категории с поправкой на точность
  теста и давность. **F** — балл ФСП `min(1; 0,6·R + 0,4·N)`: результативность и активность, без
  ранжирования по уровню и дисциплине (рекомендация менторов). **P** — подтверждённость профиля.
  **M** — актуальность по регулярным микрозадачам от работодателей: сглаженное среднее с
  полураспадом 60 дней. Отсутствие ФСП или микрозадач — не штраф, а отсутствие бонуса.
- **Skills** — покрытие стека с весом 2 для обязательных навыков и 1 для желательных. Навык,
  подтверждённый тестом, засчитывается полностью, заявленный — на 0,7, родственный (Django ≈
  FastAPI) — частично.
- **Semantic** — близость описания задач команды к опыту кандидата (TF-IDF с русским
  стеммингом и синонимами навыков, считается по пулу этой потребности).
- **Conditions** — вилка в одной налоговой базе, формат работы, город и готовность к переезду.

Веса `match-1.1` подобраны на кросс-валидации по размеченным парам (были экспертные 0,35 / 0,35 /
0,15 / 0,15). Если точного грейда меньше десяти кандидатов, подборка добирает соседние грейды с
понижением и пометкой. Версия алгоритма записывается в каждую подборку, поэтому выдачу можно
воспроизвести.

### 1.4 Объяснимость

У каждого кандидата в подборке есть кольцо балла, полоса вкладов четырёх факторов и список причин,
собранный из тех же чисел, что и балл:

```
✓ Закрывает 3 из 3 обязательных навыков: Python, FastAPI, PostgreSQL
✓ Подтверждено тестом: Python
✓ Тест: 98-й перцентиль в категории Backend-разработка · Middle (экспресс-режим, точность ниже)
✓ Ожидания укладываются в вашу вилку
✓ ФСП: победитель (1 место из 40): Кубок «Волжская волна», 2025
≈ Kafka — нет, но есть родственный RabbitMQ
✗ Грейд заявлен, но не подтверждён тестом
```

Карточка обезличена на уровне схемы данных: в ней физически нет полей ФИО и контактов, а
контакты из свободного текста маскируются. Контакты приходят отдельным объектом только при записи
о раскрытии, каждое раскрытие пишется в аудит.

### 1.5 Что проверено и что дальше

- Сквозной сценарий проходит на чистом стенде: от регистрации нового кандидата до раскрытия
  контактов работодателю. API-тесты покрывают видимость контактов (R4), изоляцию чужих данных
  (R11), автомат статусов приглашения (R5), квоты и обязательную вилку (R2), а также сохранение
  закреплённых кандидатов между версиями.
- Подборка на пуле около 370 кандидатов строится в среднем за 35 мс (95-й перцентиль — 58 мс).
- **Качество в цифрах** ([VALIDATION.md](VALIDATION.md), раздел 1): 21 размеченная вакансия,
  3 популяции по 420 синтетических кандидатов с известной истиной и шумным самоописанием.

  | Система | P@10 строго | nDCG@10 | MRR |
  |---|---|---|---|
  | «Скаут» | 0,254 | 0,591 | 0,673 |
  | Поиск по ключевым словам (BM25) | 0,171 | 0,282 | 0,337 |
  | BM25 + фильтры по самоописанию | 0,235 | 0,402 | 0,482 |

  Абляции с парными интервалами: без условий nDCG@10 падает на 0,155, без автодополнения — на
  0,046; если без теста половина кандидатов завышает грейд — на 0,121. Индекс профиля, ФСП и
  текстовая близость на синтетике статистически нейтральны — это сказано прямо.

## 2. Адаптивное тестирование и категоризация (критерий 25 %)

### 2.1 Путь к категории

```
опрос: направление → специализация → стек → заявленный грейд
  → состав теста (blueprint) виден до старта
  → адаптивный тест: 12–20 заданий (экспресс для демонстрации — 6–8)
  → решение по порогу грейда на шкале способностей → категория
```

Грейд не понижается принудительно. Провал на онбординге не сжигает попытку: уровень ниже доступен
сразу. Смена присвоенного грейда возможна раз в 90 дней, повтор неудачного повышения — через 30
(R8). Уверенное прохождение открывает отдельный тест на уровень выше, автоповышения нет.

### 2.2 Почему не единый набор вопросов и не генерация нейросетью

ТЗ (R9) прямо отвергает оба варианта. Единый набор утекает после первых прохождений. Задания,
сгенерированные нейросетью под каждого, несопоставимы по сложности, и оценки разных людей нельзя
сравнивать. Мы взяли **параметрические семейства** (Automatic Item Generation): 79 шаблонов с
генераторами данных, кода и правдоподобных неверных вариантов. Сложность и дискриминация задаются
на уровне семейства, поэтому экземпляры сопоставимы, а данные у каждого кандидата свои.

### 2.3 Алгоритм

| Шаг | Как сделано | Почему |
|---|---|---|
| Модель | IRT 3PL, для числовых ответов — 2PL (угадывание c = 0) | Учитывает сложность, различающую силу и угадывание |
| Оценка уровня | EAP по ходу теста, WLE для итогового решения | EAP устойчива с первого ответа; WLE не стягивает сильных к среднему (смещение Senior −0,3…−0,6 у EAP против −0,26…+0,03 у WLE) |
| Выбор задания | Максимум информации около порога заявленного грейда, баланс тем по blueprint, случайный выбор из 2–4 лучших и штраф за частый показ | Тест короче при той же точности решения, банк расходуется равномерно |
| Остановка | Классификационное правило: \|θ − порог\| ≥ 1,64·SE или SE ≤ 0,30, от 12 до 20 заданий | Задача теста — уверенно решить «выше или ниже порога», а не измерить θ до сотых |
| Время | Серверный дедлайн на каждое задание и на сессию | Таймер в браузере обходится |

### 2.4 Устойчивость к утечкам

- **Уникальные экземпляры.** Экземпляр задаётся HMAC(секрет сервера, соль сессии, позиция,
  семейство). Пересказ «правильного ответа» бесполезен: у другого кандидата другие числа, код и
  ответ. Тест проверяет, что из 40 seed каждое семейство даёт не меньше 4 разных экземпляров.
- **Ключ не покидает сервер.** API отдаёт формулировку и варианты, ключ и объяснение хранятся
  только в базе. Это отдельно проверяют API-тесты.
- **Ключи проверены исполнением.** Код в заданиях запускается на CI (Python, SQL в SQLite, pandas,
  JavaScript в Node), результат сверяется с ключом генератора.
- **Числовые ответы** почти не угадываются, а пилотные семейства показываются незасчитываемыми
  заданиями и копят ответы для калибровки.
- **Сигналы честности** — уход со вкладки, вставка из буфера, подозрительно быстрый верный ответ —
  видят методист и сам кандидат. Автоматически результат не снижается.

### 2.5 Валидация на синтетической популяции

Реальных ответов пока нет, поэтому движок проверен симуляцией: по 400 кандидатов с известной
«истинной» способностью на каждую из 7 специализаций, ответы по модели IRT с шумом параметров,
затем повторный тест тех же людей. Все числа воспроизводятся командами `make simulate`,
`make validate-assessment`, `make validation-report` из боевого кода; подробности — в
[VALIDATION.md](VALIDATION.md), раздел 2.

| Метрика | Полный тест | Экспресс |
|---|---|---|
| Корреляция оценки с истинной способностью r(θ̂, θ) | 0,85–0,89 | 0,72–0,83 |
| Верное решение «подтвердил заявленный грейд / нет» | 80–84 % | 74–81 % |
| Грейд с точностью до соседнего | 97,0–98,8 % | 92–98 % |
| Точный грейд из четырёх | 62–67 % | 54–60 % |
| Повторный тест: взвешенная каппа κw | 0,66–0,74 | 0,51–0,61 |
| Повторный тест: то же решение по грейду | 72–80 % | 66–74 % |
| Среднее число заданий | 13,4–17,0 | 7,5 |

Разделяющая сила: медиана дискриминации a = 1,2–1,3, медиана корреляции задания с итогом
r_pb = 0,42–0,49, AUC «сильная треть против слабой» 0,97–0,99. Утечка 8 самых частых заданий
завышает грейд 97 % кандидатов на фиксированном тесте и 51 % на «Скауте» (при β = 0,6).

### 2.6 Ограничения, которые мы видим

- Узкое место точности — различающая сила заданий, а не длина теста: удлинение почти ничего не
  даёт, а рост дискриминации на 30 % поднимает r до 0,92. Главный рычаг — калибровка параметров
  на реальных ответах. Метод (EM по Боку–Айткину) реализован и на синтетике восстанавливает
  сложность с корреляцией 0,99.
- Согласие точного грейда при повторе умеренное: кандидаты у самого порога иногда попадают по
  разные стороны. Поэтому решение принимается по интервалу, а уверенно прошедшим сразу открыт
  следующий уровень.
- В небольших банках (QA, DevOps, Mobile) часть семейств показывается почти каждому. Экземпляры
  уникальны, но шаблон становится известен — эти банки расширяем первыми.
- Экспресс-режим нужен для знакомства и проверки жюри, для найма он грубее полного теста и
  помечается в результате и в карточке.
