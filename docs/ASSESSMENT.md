# Методика оценки: как «Скаут» присваивает категорию

Категория кандидата — это пара «специализация + грейд», например «Backend-разработка · Middle».
Резюме и самооценка её не присваивают. Кандидат заявляет уровень в опросе, и этот уровень виден
работодателям с пометкой «не подтверждён» (ниже в выдаче). Подтверждает его только
адаптивный тест.

## 1. Опрос задаёт состав теста

Кандидат выбирает IT-направление и специализацию, основной стек, стаж и заявленный грейд.
Предметная область (финтех, GovTech…) необязательна и на тест не влияет.

Из опроса строится **blueprint** — веса компетенций теста. У Backend, например, такие веса:
Python 22 %, SQL 20 %, алгоритмы 15 %, HTTP и API 15 %, конкурентность 10 %, архитектура 10 %,
инструменты 8 %. Языковые компетенции закрыты условием на навык: тема «Python» включается,
только если Python есть в стеке. Вес выключенной темы делится между остальными. Кандидат видит
состав теста ещё до старта.

## 2. Банк заданий: семейства вместо вопросов

Банк состоит из **79 параметрических семейств** — это Automatic Item Generation. Семейство —
шаблон с генератором: чисел, таблиц, фрагментов кода и правдоподобных неверных вариантов,
построенных из типичных ошибок. Задания бывают двух форматов: выбор одного из четырёх вариантов
и числовой ответ. Числовой почти не угадывается, у него параметр угадывания c = 0.

- **Уникальность.** Экземпляр задаётся seed = HMAC(секрет сервера, соль сессии : позиция :
  семейство). Два кандидата получают одно семейство с разными данными и ответами, поэтому
  пересказ «правильного ответа» бесполезен. Тест проверяет, что из 40 seed у каждого семейства
  получается не меньше 4 разных экземпляров. Зная секрет, экземпляр можно воспроизвести при
  разборе апелляции.
- **Ключ проверен исполнением.** Для заданий с кодом тесты запускают сам код: Python через
  `exec`, SQL — в SQLite, pandas, JavaScript — в Node. Затем они сверяют результат с ключом
  генератора. Ошибка в ключе ловится на CI, а не на кандидате.
- **Ключ не покидает сервер.** API отдаёт формулировку, код, таблицы и варианты, а ключ и
  объяснение хранятся только в БД. Это отдельно проверяют API-тесты.
- **Пилотные семейства.** Новые семейства сначала показываются как одно незасчитываемое
  задание в полном тесте. Так копятся ответы для калибровки.

## 3. Адаптивный алгоритм

| Шаг | Что делается |
|---|---|
| Модель | IRT 3PL (2PL для числовых заданий): вероятность ответа зависит от способности θ, сложности b, дискриминации a и угадывания c |
| Оценка θ | По ходу теста — EAP по сетке из 121 точки с априорным N(0, 1): устойчива с первого ответа. Итоговое решение — WLE (взвешенное правдоподобие Уорма) на сетке из 801 точки: не стягивает сильных к среднему (§6) |
| Выбор задания | Максимум информации около порога заявленного грейда с учётом дефицита по blueprint. Затем randomesque — случайный выбор из 2–4 лучших, штраф за частую экспозицию (Sympson–Hetter-lite) и за семейство, которое кандидат уже видел |
| Остановка | Классификационное правило: \|θ − порог\| ≥ 1,64·SE или SE ≤ 0,30, но не раньше 12-го и не позже 20-го задания |
| Время | Лимит на каждое задание (от 45 до 180 с) и на сессию целиком. Дедлайн хранит сервер, просроченное задание засчитывается как неверное |

Пороги грейдов на шкале θ: Intern −1,5, Junior −0,5, Middle 0,4, Senior 1,2. Методист меняет их
в справочнике, калибровка их уточняет.

## 4. Решение и правила пересдачи

- **Подтверждён с запасом** (`passed_confident`): нижняя граница 90 % интервала выше порога
  *следующего* грейда. Тест на следующий уровень открывается сразу, без паузы.
- **Подтверждён** (`passed`): θ не ниже порога заявленного грейда. Категория присваивается.
- **Не подтверждён** (`failed`): ничего не понижается. Если оценка уверенно (θ − SE) выше порога
  одного из нижних грейдов, кандидату предлагают принять его без пересдачи.

| Ситуация | Правило |
|---|---|
| Онбординг, тест провален или прерван | Уровни ниже доступны сразу («провал не сжигает попытку»), этот уровень и выше — через 24 ч |
| Грейд присвоен | Следующая смена грейда — не раньше чем через 90 дней |
| Неудачная попытка повышения | Повтор — через 30 дней |
| Экспресс-режим | 6–8 заданий без пилотных, для знакомства и демонстрации жюри; точность ниже (см. §6) |

## 5. Честность прохождения

Прокторинга на MVP нет: менторы подтвердили, что он не обязателен. Сервер собирает сигналы для
методиста: уход со вкладки, вставку ответа из буфера и подозрительно быстрый верный ответ
(быстрее 12 % лимита задания и не дольше 8 с). Кандидат видит эти сигналы на экране результата. Автоматически
результат не снижается.

## 6. Валидация на синтетической популяции

Реальных ответов пока нет, поэтому движок проверяется симуляцией. Генерируется популяция
кандидатов с известным истинным θ, каждый проходит тест по 3PL-модели, после чего оценка
сравнивается с правдой; повторный тест того же кандидата показывает устойчивость. Полные таблицы
по специализациям — в [VALIDATION.md](VALIDATION.md), раздел 2; исходные отчёты — в
[validation/](validation/).

| Метрика (7 специализаций, по 400 кандидатов) | Полный тест | Экспресс |
|---|---|---|
| Корреляция оценки с истинной способностью r(θ̂, θ) | 0,85–0,89 | 0,72–0,83 |
| Верное решение «подтвердил заявленный грейд / нет» | 80–84 % | 74–81 % |
| Точный грейд из четырёх | 62–67 % | 54–60 % |
| Грейд с точностью до соседнего | 97,0–98,8 % | 92–98 % |
| Повторный тест: взвешенная каппа κw | 0,66–0,74 | 0,51–0,61 |
| Повторный тест: то же решение по грейду | 72–80 % | 66–74 % |
| Среднее число заданий | 13,4–17,0 | 7,5 |
| AUC «сильные против слабых» по итоговой θ̂ | 0,97–0,99 | — |

**Итоговая оценка — WLE, а не EAP.** По ходу теста θ оценивается EAP: она устойчива с первого
ответа и хороша для выбора заданий и правила остановки. Но априорное N(0, 1) стягивает итог к
среднему: на популяции с рыночными долями грейдов EAP занижала Senior на 0,32–0,62. Итоговое
решение о грейде поэтому принимается по WLE (взвешенное правдоподобие Уорма) — смещение Senior
сократилось до −0,26…+0,03 при той же согласованности повторов. Версия алгоритма — `cat-1.1`.

**Утечки.** Если в сеть утекли 8 самых частых заданий, фиксированный тест из 16 заданий завышает
грейд 97 % кандидатов, «Скаут» — 51 % при преимуществе знания шаблона β = 0,6 (подробно —
VALIDATION.md, раздел 2.4).

Ограничения указаны честно:

- Точный грейд из четырёх совпадает в 62–67 % случаев, а промах больше чем на одну ступень
  редок. Узкое место — дискриминация заданий: удлинение теста почти ничего не даёт, а рост a на
  30 % поднимает r до 0,92. Поэтому главный рычаг — калибровка на реальных ответах.
- У маленьких банков (DevOps, QA, Mobile) часть семейств показывается почти каждому. Ответы при
  этом уникальны, но шаблон становится известен. Банк нужно расширять в первую очередь здесь.
- Детекторы списывания (индекс l_z и статистика предзнания) проверены, но слишком слабы для
  автоматических решений: при 5 % ложных обвинений находят 7–20 % списывающих. В продукт не
  встроены.
- Экспресс-режим заметно грубее полного теста и годится для демонстрации, а не для найма.

## 7. Калибровка

Номинальная сложность семейства задаётся уровнем, под который оно написано: Intern −1,6,
Junior −0,7, Middle 0,3, Senior 1,2. Когда у семейства накопится не меньше 200 ответов,
параметры a и b уточняются методом маргинального максимального правдоподобия. Это EM по схеме
Бока–Айткина с шагами Fisher scoring. На синтетических данных калибровка восстанавливает b с
корреляцией 0,99, a — 0,87.

## 8. Кабинет методиста

| Раздел | Что там |
|---|---|
| Банк заданий (`/m/item-bank`) | Компетенции специализации с весами, навыками-ключами и подтверждаемыми навыками; семейства с параметрами a, b, c, статусом, долей показов и долей верных ответов. В карточке семейства — три свежих экземпляра тем же генератором, что в тесте, с ключом, разбором и seed для воспроизведения, и смена статуса (в оценке, пилот, выведено, скомпрометировано) с причиной в журнал аудита. Последнее активное семейство компетенции выключить нельзя |
| Вакансия → тест (`/m/vacancy-test`) | Цепочка «вакансия → категория → тест категории → задания и микрозадачи». Состав теста для стека вакансии считается тем же методом, что показывает кандидату опрос. Для каждого грейда вакансии — три самых информативных около порога семейства с экземплярами. Таблица навыков показывает, какие подтверждает тест, а какие остаются микрозадачам работодателя (тест не подстраивается под вакансию, VS.5) |
| Настройки оценки (`/m/settings`) | Параметры алгоритма полного и экспресс-режима, правила пересдачи и пороги грейдов по специализациям. Порог можно сдвинуть только с сохранением порядка грейдов и зазором ≥ 0,3; изменение пишется в аудит и действует для тестов, завершённых после него |

Доля показов семейства считается от сессий, в тест которых входила его компетенция: компетенции
общие для специализаций (SQL — у бэкендеров и аналитиков), а языковые входят в тест не всем.
Тот же знаменатель использует контроль экспозиции в самом тесте.

## Как воспроизвести

```bash
make simulate                                      # симуляция всех специализаций и отчёт в docs/validation
cd backend && uv run pytest tests/unit -q          # банк заданий, ядро оценки, калибровка, симуляция
cd backend && uv run pytest tests/api -q           # сценарии API: опрос → тест → категория
```
