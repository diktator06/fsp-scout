# 1. Коротко

«Скаут» — платформа подбора ИТ-специалистов с обратной механикой и верифицированным профилем
участника ФСП. Работодатель не разбирает поток откликов, а сам находит кандидата в банке, где
специалисты разложены по категориям «специализация × грейд», и приходит с приглашением, в
котором вилка зарплаты обязательна. Категорию присваивает не резюме, а опрос и адаптивный
тест; достижения ФСП поднимают ранг внутри категории, но тест не заменяют. Контакты кандидата
открываются только после его согласия.

| Что проверено | Результат |
|---|---|
| Подбор на 21 размеченной вакансии, 3 популяции по 420 синтетических кандидатов | nDCG@10 0,591 против 0,282 у поиска по ключевым словам (BM25) и 0,402 у BM25 с фильтрами; MRR 0,673 против 0,337 и 0,482 |
| Повторное прохождение теста, 7 специализаций по 400 кандидатов | Взвешенная каппа 0,66–0,74, грейд ±1 ступень — 97–99 %, точный грейд — 62–67 % |
| Разделяющая сила | AUC «сильная треть против слабой» 0,97–0,99, медиана корреляции задания с итогом 0,42–0,49 |
| Утечка 8 самых частых заданий | Фиксированный тест завышает грейд 97 % кандидатов, «Скаут» — 51 % |
| Нагрузка: 50 одновременных пользователей, банк 944 кандидата | Рабочая нагрузка: p50 48 мс, p95 166 мс, 0 ошибок; стресс — 32,6 запроса/с без ошибок |
| Качество кода | 493 теста бэкенда на реальном PostgreSQL, 77 тестов фронтенда, 6 — эмулятора ФСП; ruff и mypy strict, eslint, tsc |

Запуск — одна команда `docker compose up --build`, стенд работает офлайн, без GPU и без
внешних API, в том числе без LLM. Код открыт под лицензией MIT.

# 3. Механика подбора

**Сценарий для обеих сторон.** Кандидат проходит опрос и тест, получает категорию и отдельно
соглашается на публикацию в банке. Работодатель описывает потребность своими словами — система
разбирает специализацию, грейды, обязательные и желательные навыки, вилку, формат и город, и
показывает, откуда взято каждое поле. Затем — рекомендованные категории с рыночным срезом и
подборка: обезличенные карточки с баллом, полосой вкладов и человеческим объяснением. Уточнение
фильтров создаёт новую версию, закреплённые кандидаты переносятся. Приглашение нельзя
отправить без вилки «от–до» с явной базой НДФЛ. Кандидат видит компанию и условия сразу, а
контакты обе стороны получают только после принятия; каждое раскрытие пишется в аудит.

**Ранжирование.**

- Жёсткие фильтры: категория кандидата совпадает со специализацией и грейдами потребности,
  есть согласие на публикацию, статус поиска не «не ищу». Если точного грейда меньше десяти
  кандидатов, добавляются соседние грейды с понижением и пометкой.
- Индекс подтверждённого профиля (ранг внутри категории):
  VPS = 100 · (0,55·T + 0,20·M + 0,15·F + 0,10·P), где T — тест, M — свежие микрозадачи,
  F — ФСП, P — подтверждённость профиля. Отсутствие ФСП — не штраф, а отсутствие бонуса.
- Балл соответствия (`match-1.1`): 0,30 · навыки + 0,20 · VPS + 0,15 · текстовая близость +
  0,35 · условия (вилка в одной налоговой базе, формат, город). Неподтверждённый грейд — × 0,75,
  соседний — × 0,85.

**Проверка в цифрах.** Готовой разметки нет, поэтому построен стенд с известной истиной:
21 вакансия с экспертной разметкой и синтетические кандидаты, созданные настоящими сервисами
платформы, со скрытыми истинными θ, навыками и ожиданиями и с шумным самоописанием
(раздутый список навыков у 35 %, завышенный грейд у 25 %). Релевантность пары — 0–3 по
истинным атрибутам, правило записано до прогона.

| Система | P@10 строго | P@10 частично | nDCG@10 | MRR |
|---|---|---|---|---|
| «Скаут» | 0,254 | 0,540 | 0,591 | 0,673 |
| Поиск по ключевым словам (BM25) | 0,171 | 0,376 | 0,282 | 0,337 |
| BM25 + фильтры по самоописанию | 0,235 | 0,430 | 0,402 | 0,482 |

Потолок P@10 строго — 0,425: для части вакансий подходящих меньше десяти. Абляции с парными
интервалами показывают, что значимо держат качество условия (−0,155 nDCG@10 без них) и
автодополнение (−0,046); без теста при завышении грейда половиной кандидатов nDCG@10 падает на
0,121. Индекс профиля, ФСП и текстовая близость на синтетике нейтральны — это сказано прямо.
По итогам проверки изменены веса (кросс-валидация, `match-1.0` → `match-1.1`) и добавлено
автодополнение. Подробности, интервалы и ограничения — [VALIDATION.md](VALIDATION.md), §1.

# 4. Тестирование и категоризация

**Путь к категории:** опрос (специализация, стек, опыт, заявленный грейд) → состав теста под
стек → адаптивный тест на заявленный грейд → решение и категория. Грейд без теста виден как
«не подтверждён».

**Банк — семейства, а не вопросы.** 79 параметрических генераторов по 18 компетенциям: код на
Python и JavaScript, SQL по таблице, HTTP, сети, статистика, pandas, архитектура. Каждый
экземпляр собирается заново: seed — HMAC от секрета сервера, соли сессии, позиции и семейства,
поэтому у каждого кандидата свои числа, данные и порядок вариантов, а ключ ответа не покидает
сервер. Ответы генераторов проверяются в тестах исполнением кода (Python, SQLite, Node.js).

**Алгоритм.** IRT 3PL; по ходу теста — EAP, следующее задание — максимум информации около
порога заявленного грейда с учётом баланса тем, случайного выбора из лучших и штрафа за частые
показы; остановка — когда 90-процентный интервал не пересекает порог (12–20 заданий).
Итоговая оценка — WLE: EAP стягивала сильных к среднему и занижала Senior на 0,32–0,62, WLE
сократила смещение до −0,26…+0,03. Решение: с запасом / подтверждён / не подтверждён;
провал не сжигает попытку, смена грейда — не чаще раза в 90 дней.

**Валидация.**

| Метрика | Полный тест | Экспресс |
|---|---|---|
| Корреляция оценки с истинной способностью | 0,85–0,89 | 0,72–0,83 |
| Верное решение по заявленному грейду | 80–84 % | 74–81 % |
| Точный грейд из четырёх / ±1 ступень | 62–67 % / 97–99 % | 54–60 % / 92–98 % |
| Повтор: взвешенная каппа | 0,66–0,74 | 0,51–0,61 |

Устойчивость к утечкам (доля кандидатов с грейдом выше истинного):

| Сценарий | Фиксированный тест | «Скаут» |
|---|---|---|
| Честное прохождение | 19 % | 20 % |
| Утекли 4 самых частых, преимущество шаблона β = 0,6 | 72 % | 37 % |
| Утекли 8, β = 0,6 | 97 % | 51 % |
| Утекли 8, β = 1,0 (шаблон даёт полный ответ) | 97 % | 75 % |

Детекторы списывания (индекс l_z, статистика предзнания) проверены, но при 5 % ложных
обвинений находят лишь 7–20 % списывающих — в продукт не встроены. Слабые места названы:
точный грейд ограничен разделяющей силой заданий, малые банки (QA, DevOps, Mobile) показывают
отдельные семейства почти каждому. Подробно — [VALIDATION.md](VALIDATION.md), §2.

**Кабинет методиста.** Банк заданий с параметрами IRT, долей показов и живой генерацией
экземпляров; экран «Вакансия → тест»: категория вакансии, состав теста под её стек, самые
информативные у порога грейда семейства и какие навыки тест не покрывает (их проверяют
микрозадачи работодателя — тест единый для категории, VS.5); настройки оценки с порогами
грейдов, изменения которых пишутся в аудит.

# 5. Интерфейс

Три кабинета — специалиста, работодателя и методиста — на React 19 и Mantine 9 в цветах ФСП.
Ключевые решения: обезличенная карточка с бейджем категории и шкалой из четырёх ступеней;
«почему в подборке» человеческим языком; шкала грейда с интервалом точности; превью того, что
увидит работодатель, прямо в настройках приватности; уведомления в колокольчике и письма.
Единая шкала шрифтов во всех кабинетах: до 1440 px основной текст 16 px и заголовок страницы
30 px, шире кегль плавно растёт вместе с окном (около 20 px на мониторе 1920, не больше 24 px),
поэтому страница на мониторе выглядит так же, как на ноутбуке. Все экраны проверены на 375 px
без горизонтальной прокрутки.

# 6. Архитектура и техническая проработка

**Функциональная архитектура.** Три ролевых кабинета в одном веб-приложении; каждая функция
опирается на свой модуль бэкенда.

| Кабинет | Функции | Модули бэкенда |
|---|---|---|
| Кандидат | Регистрация с подтверждением email; анкета вручную или из PDF-резюме; стандартизированный PDF-профиль; опрос по отрасли и специализации, выбор грейда, адаптивный тест; категория, история опросов и тестов, пересдачи; приглашения; вакансии и отклики; микрозадачи; приватность, согласия, ФСП ID; выгрузка и удаление данных | `auth`, `candidate`, `assessment`, `invitations`, `vacancies`, `microtasks`, `fsp`, `account` |
| Работодатель | Профиль компании; потребность из текста; подборка с рекомендованными категориями и объяснениями, уточнение версиями; банк кандидатов с фильтрами по категории, специализации, грейду, стеку и ФСП; приглашения с вилкой и статусами; вакансии и отклики; микрозадачи; «Вакансия → тест»; интеграция с ATS | `employer`, `matching`, `invitations`, `vacancies`, `microtasks`, `assessment`, `trust`, `integrations` |
| Методист | Справочники, банк заданий, «Вакансия → тест», пороги и настройки оценки, модерация жалоб | `assessment`, `trust` |
| Общее | Уведомления, журнал согласий, раскрытие контактов с записью в аудит | `notifications`, `consents`, `contact_access` |

**Компонентная архитектура.** Монолит с явным разделением слоёв и слабо связанными модулями;
каждый компонент — отдельный контейнер.

```
Браузер (React SPA) → nginx (статика, прокси /api) → FastAPI → PostgreSQL 16 + pgvector
FastAPI → Mailpit (SMTP) · ФСП ID и реестр (OIDC, JWKS) · ATS работодателя (вебхуки HMAC)
Браузер → ФСП ID (страница входа участника)
```

| Компонент | Технология | Что делает |
|---|---|---|
| `frontend` | React 19, Mantine 9 за nginx 1.31 | Кабинеты кандидата, работодателя и методиста; прокси `/api` |
| `backend` | FastAPI на uvicorn, Python 3.13 | Бизнес-логика и API, адаптивный тест, подбор, фоновая отправка вебхуков |
| `db` | PostgreSQL 16 + pgvector | Все данные: 48 таблиц, миграции Alembic при старте |
| `fsp-registry-mock` | FastAPI | ФСП ID (OIDC, PKCE, RS256) и реестр достижений |
| `mailpit` | Mailpit 1.31 | Письма подтверждения и уведомления |
| `keycloak` (по желанию) | Keycloak 26.4 | ФСП ID на полноценном Keycloak — тот же протокол |
| `caddy` (сервер) | Caddy 2.10 | HTTPS при развёртывании на VPS |

**Слои бэкенда:** api (роутеры, роли) → services (сценарии и правила) → crud (единственный
доступ к базе) → models (SQLAlchemy); схемы Pydantic описывают вход и выход API. Подробно —
[ARCHITECTURE.md](ARCHITECTURE.md).

- **API:** 126 методов в OpenAPI 3.1 с описанием ответов и кодов ошибок; Swagger UI офлайн;
  типы клиента генерируются из спецификации (раздел 9).
- **Вход:** email с подтверждением; access-JWT с claims как у Keycloak; refresh-токен в
  httpOnly-cookie с ротацией и обнаружением повторного использования; вход через ФСП ID по
  OIDC (Authorization Code + PKCE, RS256, JWKS) — и с эмулятором, и с полноценным Keycloak 26.
- **Интеграции:** вебхуки ATS через outbox в той же транзакции, подпись HMAC-SHA256, повторы,
  защита от SSRF, журнал доставок, выгрузка CSV и JSON.
- **Производительность:** 50 одновременных пользователей (30 работодателей и 20 новых
  кандидатов, проходящих регистрацию и полный тест) на банке из 944 опубликованных кандидатов:
  p50 48 мс, p95 166 мс, худшая операция — 268 мс, ошибок нет; под стрессом без пауз —
  32,6 запроса/с, тоже без ошибок. Нагрузочный тест нашёл и помог исправить четыре проблемы:
  дорогой стемминг, argon2id в цикле событий, один процесс API и OOM базы при лимите 256 МБ —
  [LOAD_TEST.md](LOAD_TEST.md).
- **Масштабирование:** состояние только в PostgreSQL; outbox с `SKIP LOCKED` допускает несколько
  процессов; ограничитель частоты — единственное, что при горизонтальном масштабировании
  переедет в Redis.

# 8. Интеграция с ФСП и ФСП ID

Доступа к боевому ФСП ID и реестру у команд нет, поэтому в стенде работает сервис
`fsp-registry-mock` с тем же протоколом, что у Keycloak (OIDC), и реестром достижений. Бэкенд
говорит с ним как с настоящим провайдером; рядом лежит готовый realm для Keycloak 26 и
compose-оверлей. Подробно — [FSP_INTEGRATION.md](FSP_INTEGRATION.md) и
[KEYCLOAK_GUIDE.md](KEYCLOAK_GUIDE.md).

**Привязка профиля к ФСП ID** (OIDC Authorization Code + PKCE S256):

| Шаг | Кто → кому | Что происходит |
|---|---|---|
| 1 | Кандидат → «Скаут» | «Привязать ФСП ID» с отдельным согласием на получение данных ФСП (152-ФЗ) |
| 2 | Бэкенд | Создаёт одноразовые `state`, `nonce` и PKCE-верификатор на 10 минут, возвращает адрес входа |
| 3 | Браузер → ФСП ID | Участник входит логином и паролем ФСП и разрешает доступ |
| 4 | ФСП ID → кабинет | Возврат на `/c/fsp/callback` с `code` и `state` |
| 5 | Кабинет → бэкенд | `code` и `state` с access-токеном пользователя; `state` гасится до обращения к провайдеру |
| 6 | Бэкенд → ФСП ID | Обмен кода с `code_verifier`; проверка id_token: подпись RS256 по JWKS, `iss`, `aud`, `exp`, `nonce` |
| 7 | Бэкенд → реестр | Участия и результаты по токену участника; ответ проверяется схемой |
| 8 | Бэкенд | Привязка, участия, журнал синхронизации, согласие и аудит; пересчёт балла F и индекса профиля |

Повторная синхронизация идёт сервисным токеном платформы (client credentials,
`scope=registry:read`). Вход через ФСП ID работает для уже привязанных аккаунтов: аккаунт по ФСП
ID не создаётся, потому что в реестре нет подтверждённого email.

**Получаем:** номер участника, регион, разряд; по каждому участию — мероприятие, уровень,
дисциплину, дату, формат, команду и роль, место, число участников, ссылку на протокол.
**Не получаем:** ФИО, дату рождения, документы, контакты.

**Состояния профиля:** не привязан — F = 0, «оценка основана на тесте и профиле»; привязан без
участий — F = 0 и разряд, если есть; привязан с участиями — F от 0 до 1 и лента участий;
скрыт кандидатом — F = 0, ничего не показывается. Нулевой F означает отсутствие бонуса, а не
штраф. Балл ФСП не различает уровень и дисциплину соревнования (просьба менторов ФСП) и
учитывает число участий, результативность и давность: F = min(1; 0,6·R + 0,4·N), полураспад
веса — 24 месяца.

**Отказоустойчивость:** недоступный реестр не стирает прошлые участия; недоступный ФСП ID — 503
`fsp_unavailable` без записи в базу; один участник у двух профилей — 409 `fsp_already_linked`;
незнакомый `kid` — JWKS перечитывается один раз.

**Переход на боевой ФСП ID** — переменные окружения, без изменений кода: `FSP_PUBLIC_URL`
(realm ФСП ID), `FSP_INTERNAL_URL`, `FSP_REGISTRY_URL`, `FSP_CLIENT_ID` и `FSP_CLIENT_SECRET`,
`FSP_PARTICIPANT_CLAIM` (в Keycloak — `fsp_participant_id`). С dev-секретом production не
стартует.

# 9. API

126 методов в 21 группе, OpenAPI 3.1. Полный справочник — [API.md](API.md), он собирается
командой `make openapi` из той же спецификации, что отдаёт Swagger UI на стенде
(http://localhost:8080/api/docs, работает без интернета).

- **Вход.** `POST /api/v1/auth/login` возвращает access-JWT на 15 минут и ставит refresh-токен в
  httpOnly-cookie; дальше — заголовок `Authorization: Bearer <token>`. Роль — в
  `realm_access.roles`, как у Keycloak.
- **Ошибки** — единый формат `{"error": {"code", "message", "details"}}`; у каждого метода в

# 11. Сборка, запуск и проверка

**Что нужно:** Docker с Compose v2 и около 1,5 ГБ свободной памяти; GPU не нужен. Интернет
нужен только для сборки образов, стенд работает офлайн. Свободные порты: 8080 (приложение),
8025 (Mailpit), 8090 (эмулятор ФСП ID).

**Шаг 1. Собрать и запустить.**

```
git clone <адрес репозитория> scout && cd scout
docker compose up --build -d
```

Через одну-две минуты все сервисы в состоянии `healthy` (`docker compose ps`). Бэкенд сам
применяет миграции, наполняет справочники и банк из 79 семейств заданий, создаёт демо-аккаунты
и около 120 синтетических кандидатов, часть из них привязывает к участникам эмулятора ФСП. Файл
`.env` не нужен: значения по умолчанию заданы в `docker-compose.yml`.

**Шаг 2. Открыть.**

| Что | Адрес |
|---|---|
| Приложение | http://localhost:8080 |
| Письма подтверждения и уведомления (Mailpit) | http://localhost:8025 |
| ФСП ID и реестр (эмулятор) | http://localhost:8090 |
| Swagger UI | http://localhost:8080/api/docs |

**Шаг 3. Войти.** Пароль демо-аккаунтов — `ScoutDemo2026`, на странице входа они подставляются
одной кнопкой.

| Роль | Email | Что внутри |
|---|---|---|
| Специалист | `candidate@example.com` | Чистый аккаунт: онбординг, тест, публикация, ФСП |
| Специалисты для жюри | `jury1@example.com` … `jury5@example.com` | Пять чистых аккаунтов: путь с нуля и пересдачи, не мешая друг другу |
| Работодатель | `employer@example.com` | Компания с потребностями, подборками, вакансиями, откликами и микрозадачами |
| Методист | `methodist@example.com` | Банк заданий, «Вакансия → тест», настройки оценки, модерация |
| Синтетические кандидаты | `demo.backend.01@example.com` и т. п. | Прошли тест настоящим сервисом оценки |

Участники ФСП в эмуляторе: `fsp000021` (7 соревнований, 6 призовых), `fsp000030`, `fsp000012`,
`fsp000007` (участий нет), пароль `FspDemo2026`. Регистрация нового кандидата тоже работает:
письмо со ссылкой подтверждения приходит в Mailpit.

**Шаг 4. ФСП ID на Keycloak (по желанию).**

```
make up-keycloak
make keycloak-smoke
```

Keycloak 26 поднимается на http://localhost:8081, участники и пароль те же. Вернуться к
эмулятору — `make down-keycloak && make up`.

**Шаг 5. Проверки кода** (нужны Python 3.13 с uv и Node.js 22+):

```
make check
```

Это ruff, mypy strict, eslint, tsc и все тесты: 493 бэкенда на реальном PostgreSQL, 77
фронтенда, 6 эмулятора. Валидация и нагрузка воспроизводятся командами `make simulate`,
`make validate-assessment`, `make eval-matching`, `make load-stand` и `make load-test`.

**Шаг 6. Развёртывание на сервере.** Оверлей `deploy/` добавляет Caddy с автоматическим HTTPS:
скопировать `deploy/vps.env.example` в `deploy/vps.env`, указать домен и секреты, выполнить
`make vps-up` и `make vps-check DOMAIN=<домен>` — [DEPLOYMENT.md](DEPLOYMENT.md).

**Начать заново** с чистыми данными:

```
docker compose down -v --remove-orphans && docker compose up --build -d
```

# 12. Ограничения и дальше

- Все метрики получены на синтетике: абсолютные значения зависят от допущений модели, сравнение
  систем на одних данных — нет. Первый шаг после хакатона — калибровка параметров заданий и
  проверка весов подбора на реальных ответах и наймах.
- Банки QA, DevOps и Mobile нужно расширять в первую очередь.
- Текстовая близость — TF-IDF; эмбеддинги имеют смысл, когда появятся живые описания.
- ФСП ID и реестр — эмулятор с протоколом Keycloak; переключение на боевой — переменными окружения.
